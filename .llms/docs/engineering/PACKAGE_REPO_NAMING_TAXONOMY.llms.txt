# Package & Repository Naming Taxonomy

> **Purpose**: Stop **sprawling `phenotype-*` prefixes** on generic or reusable code. Reserve the prefix for **organization-bound** domains; name **productized / libified** packages so they are **useful and credible outside** Phenotype while still composing the polyrepo.  
> **Aligns with**: `TOP_LEVEL_REPO_LAYOUT.md`, `WRAP_AND_ROLL_GOVERNANCE.md`, `docs/GOVERNANCE.md`, `docs/architecture/POLYREPO-STRUCTURE.md`  
> **Last updated**: 2026-03-25

---

## 1. Problem statement

Agents and scaffolding have created many **`phenotype-<something>`** repos. That is appropriate **only** when the artifact is **intrinsic to Phenotype org semantics** (governance, brand, or a named org product surface). Reusable mechanics (state machines, HTTP helpers, hex templates) should be **neutral-named**, **semver-productized** libraries that **any** team could adopt—while Phenotype remains a **consumer** in the polyrepo.

---

## 2. Tiers (use one per repo or root package)

### Tier A — **`phenotype-*` (org-bound)**

Use **only** when **at least one** of these is true:

- The **domain language** is Phenotype-specific (governance, org config, org design system contract).
- The repo **ships org policy** or **canonical docs** that other repos must not fork without alignment.
- The name **signals ownership** to humans and automation (e.g. `phenotype-config`, `phenotype-design`).

**Do not** use `phenotype-*` for: generic algorithms, hexagonal boilerplate, state machines, or adapters that could serve a **non-Phenotype** product unchanged.

---

### Tier B — **Productized / marketable (neutral name)**

Use a **short, descriptive, brand-neutral** repo name (and matching crate/module name where possible):

- **Readable README** for an external developer in 5 minutes.
- **Stable API** (semver for libs; versioned CLI for tools).
- **Clear scope** (one primary concern).
- **No org prefix** unless the repo is literally the org’s product (see Tier C).

Examples of **style** (illustrative, not prescriptive names):

| Style | Example |
|-------|---------|
| Descriptive compound | `portkey`, `dual-write`, `mesh-bus` |
| Problem-oriented | `policy-gate-sdk`, `workflow-contracts` |
| Layer + role | `hex-ports-go`, `event-outbox-rs` |

These repos **remain** in the Phenotype polyrepo graph via **dependency pins**, **composite actions**, or **submodules**—without implying Phenotype owns the **concept** globally.

---

### Tier C — **Named products & apps (existing brands)**

Repos that are **products** or **user-facing apps** keep **product names** (`helios-cli`, `thegent`, `portage`, `AgilePlus`, …). Do **not** rename them to `phenotype-*` unless there is a deliberate **rebrand ADR**.

---

### Tier D — **Templates & scaffolds**

Use `template-*`, `scaffold-*`, or **language-prefixed** template names (`hexagonal-go`, `template-lang-rust`) under the **template** hub. These are **not** production libraries; they are **cookiecutters**.

---

## 3. Crate / module / npm package names inside a repo

**Repo name** may differ from **published artifact name**:

| Ecosystem | Guidance |
|-----------|----------|
| **Rust** | crate name on crates.io: neutral for Tier B; org prefix only in Tier A if intentional. |
| **Go** | module path can be `github.com/<org>/<repo>` with **package** names neutral inside `pkg/`. |
| **npm** | Scoped package `@phenotype/*` **only** for org-bound Tier A; Tier B use **unscoped or `@org`/neutral** per publish strategy. |
| **PyPI** | Same: `phenotype_*` only for Tier A. |

---

## 4. Migration (from over-prefixed `phenotype-*`)

When a repo is **misclassified**:

1. **ADR**: rename or extract? (breaking vs new repo).  
2. **Prefer**: `git mv` history-preserving rename **or** new repo + **deprecation** notice in old README.  
3. **Update imports** in consumers; **one** coordinated release per ecosystem.  
4. **Archive** old repo to `.archive/` or mark **deprecated** in README if read-only.

---

## 5. Decision checklist (before creating `phenotype-<new>`)

| Question | If **yes** → Tier A OK |
|----------|------------------------|
| Does it encode **Phenotype org policy or vocabulary**? | |
| Would a **non-Phenotype** product use it **without** rewriting domain terms? | If **yes**, prefer **Tier B** |
| Is it primarily a **template**? | **Tier D** |
| Is it a **named product**? | **Tier C** |
