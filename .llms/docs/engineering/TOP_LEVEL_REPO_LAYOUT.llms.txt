# Top-Level Repository Layout (Polyrepo / Hexagonal)

> **Purpose**: Keep **root directories readable** and reserve the root for **entrypoints and contracts**, not dumps.  
> **Applies to**: Phenotype org repos, DinoForge–aligned repos, and reference templates.  
> **Last updated**: 2026-03-25

---

## 1. Principles

### 1.1 Root = product + contracts

- **Root** holds: **README**, **LICENSE**, **AGENTS.md**, **CLAUDE.md** (if used), **CHANGELOG**, **Taskfile** / **Makefile** (if standard), **package manager** manifests, **CI** (`.github/`), and **one** primary app entry (`cmd/`, `src/`, `crates/` root, etc.).  
- **Avoid** piling session notes, scratch reports, or one-off audits at root—use `docs/` (see below).

### 1.2 Hexagonal placement

| Concern | Typical location |
|---------|------------------|
| Domain (pure) | `src/domain/`, `internal/domain/`, `crates/<name>-domain/` |
| Application / use cases | `src/application/`, `internal/app/` |
| Ports (interfaces) | `src/ports/`, `domain/ports/` |
| Adapters (inbound) | `adapters/http/`, `adapters/cli/` |
| Adapters (outbound) | `adapters/persistence/`, `adapters/external/` |
| Infrastructure | `infrastructure/`, `infra/` (IaC separate from domain) |

### 1.3 Polyrepo extraction

- **Extract** to a shared library when: same **non-trivial** logic in **2+** repos, **stable API**, and **semver** ownership.  
- **Keep** in service repo when: logic is **one service** or changes with every release.

---

## 2. Recommended root layout (language-agnostic)

```
repo-root/
├── README.md
├── LICENSE
├── AGENTS.md
├── CHANGELOG.md
├── docs/
│   ├── guides/
│   ├── reference/
│   ├── research/
│   ├── changes/          # per-change proposals (optional)
│   └── governance/       # ADRs, policies (if not only in docs/adr)
├── .github/
├── src/                  # or crates/, lib/, packages/
├── tests/                # or co-located *_test.*
├── tools/                # scripts, codegen, not production code
├── Taskfile.yml          # or Makefile (one primary task runner)
└── (optional) examples/
```

---

## 3. What **not** to put at root

| Avoid | Put instead |
|-------|-------------|
| `SUMMARY_*.md`, `STATUS_*.md`, `FINAL_*.md` | `docs/reports/` or session folder under `docs/sessions/` |
| Multiple competing lockfiles | One package manager per ecosystem; document in README |
| Generated artifacts | `dist/`, `target/`, `build/` (gitignored) |
| Secrets | `.env` (gitignored), secret manager in CI |

---

## 4. Monorepo vs polyrepo

| Monorepo | Polyrepo |
|----------|----------|
| `crates/` / `packages/` / `services/` with clear boundaries | Separate git repos + shared libraries |
| Shared tooling at root | Per-repo `Taskfile` + org-wide templates |
| One CI pipeline with path filters | Per-repo pipelines; reusable workflows in composite actions |

---

## 5. Microservices and “productization”

- **Service** = deployable unit with **own** API contract and **versioned** client SDK when public.  
- **Plugin** = loads at runtime; **extension points** are **ports**; implementations are **adapters** in isolated modules.  
- **Libification**: move stable code to **named crates/packages** with **README + semver + changelog**.
