# Python Workflow & Productivity CLI Tools (libs.tech)

## Scope

This report focuses on Python tooling from the libs.tech 2026 Python CLI list for daily workflow and productivity use:

- `copier`
- `invoke`
- `pipdeptree`
- `xdg`
- `progress`
- `doitlive`
- `PyInquirer`

Each section summarizes what it does, where it fits, and practical adoption guidance for real teams.

## 1) `copier` — project bootstrap from structured templates

- **Primary value**: reproducible project scaffolding with template logic, pre/post hooks, and updates.
- **Strengths**:
  - Great for creating consistent repo/tooling layouts.
  - Template variables and conditional file generation reduce drift.
  - Good fit when compliance and onboarding consistency matter.
- **Risks**:
  - Template logic can get complex and become difficult to maintain.
  - Requires template governance and periodic lint/refresh checks.
- **Best use cases**:
  - New service bootstrap
  - Local-first project generators for internal tooling
  - Standardized onboarding docs, CI, and config layout
- **Adoption notes**:
  - Start with 2–3 base templates only.
  - Add tests for generated output (e.g., smoke scripts that regenerate into temp dirs and validate files).
  - Pin template versions and add change windows for template updates.

## 2) `invoke` — task orchestration and command grouping

- **Primary value**: task runner with clean namespaced commands and dependency chaining.
- **Strengths**:
  - Natural replacement for ad hoc `make`-like shell bundles.
  - Strong ergonomics for project automation (`inv lint`, `inv test`, etc.).
  - Easy to keep workflows close to Python code.
- **Risks**:
  - Can become a second orchestration layer competing with `Makefile`, `just`, or task-specific CLIs.
  - Requires discipline around task naming and doc generation.
- **Best use cases**:
  - Python-heavy repos with repeated local dev workflows.
  - Standardizing dev/test/deploy commands.
- **Adoption notes**:
  - Define an ownership model for task definitions.
  - Keep tasks idempotent and short-lived when possible.
  - Avoid putting one-off one-line shell chains directly into tasks without comments and rationale.

## 3) `pipdeptree` — dependency tree inspection

- **Primary value**: visibility into Python dependency graph and version conflicts.
- **Strengths**:
  - Helps identify transitive conflicts and dead edges quickly.
  - Useful in triage when dependency lock churn causes CI breaks.
  - Lightweight and familiar to Python teams.
- **Risks**:
  - Not a full dependency policy engine; it is inspection, not enforcement.
  - Can be slow on very large environments.
- **Best use cases**:
  - Upgrade planning, release blockers, security triage prep.
  - Audits during incident response for dependency changes.
- **Adoption notes**:
  - Run in CI at a controlled cadence (not every commit).
  - Pair with `pip check` / security tooling rather than using it as a sole gate.
  - Export and diff `pipdeptree` output in pre/post upgrade runs.

## 4) `xdg` — XDG base-directory-aware path conventions

- **Primary value**: canonical cache/config/runtime path resolution across Linux/macOS/Windows.
- **Strengths**:
  - Reduces hardcoded path risk (`~/.config`, `~/.cache`, etc.).
  - Keeps CLIs consistent with desktop/system conventions.
- **Risks**:
  - Increases dependency surface for small scripts.
  - Mixed expectations in mixed environments can still need explicit overrides.
- **Best use cases**:
  - Internal CLI tools that write logs, caches, and config files.
  - Multi-tool projects with shared local state.
- **Adoption notes**:
  - Enforce central constants for config/cache directories.
  - Add migration behavior when changing base directory defaults.
  - Keep env-var override precedence explicit for CI and containers.

## 5) `progress` — terminal progress UX primitives

- **Primary value**: simple progress bar APIs for long-running operations.
- **Strengths**:
  - Small footprint and straightforward integration.
  - Improves operator feedback during batch jobs and data pipelines.
- **Risks**:
  - Primarily presentation; no built-in retry/backoff orchestration.
  - Not sufficient for full observability; needs logging/metrics in parallel.
- **Best use cases**:
  - local scripts and maintenance tasks.
  - CLI tools where human visibility of stage progress is important.
- **Adoption notes**:
  - Limit output noise: use bars for long tasks only.
  - Provide `--json`/`--quiet` modes for machine consumption.
  - Ensure clean rendering in non-TTY contexts (CI logs, redirection).

## 6) `doitlive` — live terminal session capture and replay

- **Primary value**: record runnable terminal sessions for demos, onboarding, and runbooks.
- **Strengths**:
  - Great for live teaching and reproducible CLI walkthroughs.
  - Can improve internal enablement and incident response runbook quality.
- **Risks**:
  - Session scripts can become stale quickly.
- **Best use cases**:
  - Training, runbook demos, onboarding for complex command sequences.
- **Adoption notes**:
  - Store scripts in version control and include required environment assumptions.
  - Add review checks to avoid secrets appearing in recorded demos.
  - Refresh recorded sessions with a quarterly cadence.

## 7) `PyInquirer` — interactive prompts and guided CLIs

- **Primary value**: interactive selection prompts (`list`, `checkbox`, confirm, etc.).
- **Strengths**:
  - Significantly improves discoverability for multi-step flows.
  - Reduces user error for structured input paths.
- **Risks**:
  - Not well-suited to strict CI/non-interactive automation.
  - Forks and upstream maintenance status should be checked before long-term use.
- **Best use cases**:
  - Operator tools used in interactive shell sessions.
  - Wizards that guard against command misuse.
- **Adoption notes**:
- Use `auto-prompt` fallback mode for scripted usage if possible.
  - Keep interactive and scripted interfaces separated behind `--interactive` flag.
  - Return machine-friendly output and exit codes in all paths.

## Cross-tool adoption recommendations

### Recommended baseline stack

- **For internal developer tooling (small team)**: `invoke + copier + progress`
- **For operational and support scripts**: add `pipdeptree + xdg`
- **For training-heavy teams**: add `doitlive` and `PyInquirer` in interactive-only flows

### Practical rollout plan (4-week)

1. **Week 1**: Introduce `invoke` for dev/test/build commands and enforce task docs.
2. **Week 2**: Add `copier` for scaffolds on at least one active template family.
3. **Week 3**: Standardize path usage with `xdg` + add `pipdeptree` in dependency hygiene checks.
4. **Week 4**: Add `progress` UX improvement and select either `PyInquirer` or `doitlive` for training/review use cases.

### What to avoid initially

- Avoid adopting all seven tools at once; governance and docs overhead rises quickly.
- Do not make interactive tools (`PyInquirer`, `doitlive`) mandatory defaults for automation paths.
- Avoid over-relying on output format from `progress` for machine parsing; prefer structured logs/JSON mode in parallel paths.

## Decision matrix (at a glance)

- **Primary productivity layer**: `copier`, `invoke`, `xdg`
- **Operational visibility layer**: `pipdeptree`, `progress`
- **Human-facing interactivity layer**: `PyInquirer`, `doitlive`
- **Hard blockers**: missing CI policy, unclear template ownership, and stale prompt/session scripts

## Final recommendations

Adopt these tools as a **stratified stack** rather than a monolithic one:
- start with deterministic, low-risk foundations (`copier`, `invoke`, `xdg`);
- add inspection and reliability (`pipdeptree`, `progress`) once baseline automation is stable;
- introduce interactive tooling (`PyInquirer`, `doitlive`) only for explicit, human-led flows.
