# Audit and Plan: CLIProxy Accuracy, Release Infra, Domain Mapping (2026-02-20)

## Scope

This audit covers:

1. `README.md` and provider docs accuracy (GLM, OpenCode/Zen, provider login modes).
2. CI/CD and DevOps quality-gate parity vs local task expectations.
3. Distribution/release hardening (prepackaged artifacts, package registries, deterministic docs/API generation).
4. New feature track: user-domain mapping (Porkbun domain + Cloudflare Tunnel).

## Executive Findings

### F1. README language and accuracy drift

- `README.md` was high-level and marketing-heavy, but omitted practical provider/proxy specifics.
- It did not clearly surface supported CLIProxy provider surfaces (`glm`, `zen`, `openrouter`, etc.) even though they exist in code:
  - `src/thegent/agents/cliproxy_data/provider_definitions.json`
  - `src/thegent/agents/cliproxy_data/model_indices.json`

### F2. Provider setup doc partial mismatch

- `docs/guides/PROVIDER_SETUP_GUIDE.md` did not list `zen` in the login table even though provider definitions include `zen`.
- Login flow in code is split by provider:
  - OAuth flags in `src/thegent/agents/cliproxy_manager.py` (`_LOGIN_FLAGS`)
  - API-key provider metadata in `src/thegent/agents/cliproxy_data/provider_definitions.json`

### F3. CI/CD is fragmented and redundant

- Current workflows include overlaps (`ci.yml`, `test.yml`, `build.yml`) with inconsistent gates.
- Some checks use skip-style execution in places, reducing gate signal quality.
- Docs pipeline exists (`.github/workflows/docs.yml`) but needs hardening for reliable build/deploy gating.

### F4. Release/distribution pipeline incomplete

- Build/publish flows are not unified into a deterministic release pipeline.
- Gaps include:
  - no consolidated release artifact job (wheel/sdist + checksums + docs bundle)
  - no explicit package registry publication flow
  - no guaranteed API/docs generation in release path

### F5. Domain mapping feature missing first-class UX

- There are local references in adjacent repo docs (`zen-mcp-server`) proving Cloudflare Tunnel patterns already used.
- thegent lacks a dedicated user-facing “map my domain” feature path for domain registrars like Porkbun.

## External Research Notes (for Domain Mapping)

Primary sources used:

- Cloudflare Tunnel setup and connector flow:
  - https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/get-started/create-remote-tunnel/
  - https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/get-started/
- Cloudflare DNS import/migration:
  - https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/
  - https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/setup-zone/
- Porkbun DNS/API surface (for registrar-origin management):
  - https://porkbun.com/
  - https://porkbun.com/api/json/v3/documentation

Conclusion:

- Best user path is usually: move authoritative DNS to Cloudflare (or keep registrar DNS and CNAME to tunnel endpoint), then use named Cloudflare Tunnel + ingress hostname mapping.
- For users with existing Porkbun domains, the operationally simplest secure path is:
  - keep domain at Porkbun (registrar)
  - set nameservers to Cloudflare (DNS authority)
  - configure tunnel + DNS record in Cloudflare
  - optionally manage DNS records via Cloudflare API

### Phase 2: CI/CD and Quality Gate Unification

- P2-T1: Consolidate duplicate workflows into one canonical CI pipeline.

Acceptance checks:

- Single canonical CI status for PR merge.

### Phase 3: Release and Packaging Hardening

- P3-T1: Add release workflow: wheel + sdist + checksum bundle.

Acceptance checks:

### Phase 4: Domain Mapping Feature (Porkbun + Cloudflare)

- P4-T1: Spec `thegent domain map` command contract.
- P4-T2: Implement “advisor” mode first:
  - validates domain setup assumptions
  - outputs exact DNS + tunnel steps for user environment
- P4-T3: Implement “apply” mode (optional, API-token driven):
  - Cloudflare DNS/tunnel API integration
  - secure secret handling + dry-run
- P4-T4: Add docs + doctor checks for domain mapping readiness.

Acceptance checks:

- User can run one guided command and get a deployable domain mapping checklist.
- Optional apply mode performs idempotent updates with dry-run support.
