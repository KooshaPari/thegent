## Hexagonal Architecture Template Structure

Each hexagonal template follows the **Ports & Adapters** pattern:

```
{hexagon-lang}/
├── src/
│   ├── domain/           # Pure business logic (no dependencies)
│   │   ├── entities/     # Core business entities
│   │   ├── value-objects/ # Immutable value types
│   │   ├── services/     # Domain services
│   │   ├── events/      # Domain events
│   │   └── exceptions/  # Domain exceptions
│   ├── application/     # Use cases & orchestration
│   │   ├── ports/       # Input/Output interfaces
│   │   ├── usecases/   # Application services
│   │   ├── dto/        # Data transfer objects
│   │   └── queries/    # Read models
│   ├── infrastructure/ # External adapters
│   │   ├── persistence/  # Database adapters
│   │   ├── http/        # HTTP adapters
│   │   ├── messaging/   # Message queue adapters
│   │   └── external/    # Third-party adapters
│   └── admission/      # Primary adapters (controllers, handlers)
│       ├── http/        # HTTP handlers
│       ├── cli/         # CLI handlers
│       └── graphql/     # GraphQL resolvers
├── tests/
│   ├── unit/          # Unit tests (domain)
│   ├── integration/    # Integration tests (ports)
│   └── e2e/           # End-to-end tests
├── scripts/            # Dev scripts
├── docs/               # Architecture docs
├── README.md
├── package.json        # or go.mod, Cargo.toml, etc.
└── Makefile           # or just scripts
```

## Naming Conventions

**Authoritative policy**: [`docs/engineering/PACKAGE_REPO_NAMING_TAXONOMY.md`](../engineering/PACKAGE_REPO_NAMING_TAXONOMY.md) — reserve **`phenotype-*`** for **org-bound** domains; use **neutral, productized** names for reusable libs and “marketable” repos.

### Phenotype-prefixed repos (Tier A — org-bound only)

Use `phenotype-{domain}` **only** when the artifact is **intrinsic to Phenotype org** semantics (governance, org config, org design contract). Examples that fit the **intended** use of the prefix:

- `phenotype-config` — org configuration management & validation  
- `phenotype-design` — org design system / UI contract  

**Avoid** new `phenotype-*` repos for generic hex templates, state machines, or adapters that could serve **non-Phenotype** consumers unchanged—those belong in **Tier B** (neutral name).

### Generic / productized / marketable packages (Tier B)

```
{short-descriptive-name}
{problem}-{role}
```

Examples (illustrative):

- `hexagon-ts` — hexagonal template (TypeScript)  
- `scaffold-*` — microservice or plugin scaffold  
- Neutral crates/modules published with **semver** for reuse inside and outside the org  

### Templates (Tier D)

Language or pattern templates under `template-*` or `template-lang-*` hubs—not production libraries.

## Development Methodologies Applied

### Architecture
- **Hexagonal Architecture** (Ports & Adapters)
- **Clean Architecture** (4 layers)
- **CQRS** (Command Query Responsibility Segregation)
- **Event Sourcing** (optional)
- **Microservices** (service per bounded context)

### Design Principles
- **SOLID** (Single Responsibility, Open/Closed, Liskov, Interface Segregation, Dependency Inversion)
- **KISS** (Keep It Simple, Stupid)
- **DRY** (Don't Repeat Yourself)
- **YAGNI** (You Aren't Gonna Need It)
- **SoC** (Separation of Concerns)

### Development Processes
- **TDD** (Test-Driven Development)
- **BDD** (Behavior-Driven Development)
- **DDD** (Domain-Driven Design)
- **ATDD** (Acceptance Test-Driven Development)
- **SDD** (Specification-Driven Development)

### Code Quality
- **XDD** (eXtreme Driven Development) - TDD + BDD + CDD combined
- **Conventional Commits** (commit linting)
- **Semantic Versioning** (auto releases)
- **Code Review** (required for all changes)

```

  push:
    branches: [main]

    branches: [main]
  workflow_dispatch:  # Manual triggers for main
```

- Build & Test
- Lint
- Security Scan
- Code Coverage

### Branch Strategy
- `main` - Production-ready
- `feature/*` - New features
- `fix/*` - Bug fixes
- `chore/*` - Maintenance
- `docs/*` - Documentation
