# Implementation Strategy

## Strategy summary

The implementation should be layered:

1. Make the data model and terminology coherent.
2. Fill API mutation gaps before building more UI/automation on top.
3. Convert MCP to thin, functional orchestration around the canonical backend.
4. Replace placeholder CLI flows with storage-backed operations.
5. Normalize release governance and branch policy.
6. Add docs and migration tooling in parallel with the core platform work.

## Recommended order

### Phase 1 - Core parity

- Add API writes for modules and cycles.
- Add import bundle parsing and dry-run validation.
- Finish queue persistence.
- Replace the obvious MCP stubs.

### Phase 2 - Batch and migration

- Add batch create/update/transition endpoints.
- Add import/apply reconciliation flows.
- Add org migration tracking records and views.

### Phase 3 - Release governance

- Normalize channel vocabulary.
- Update CI/publish/promotion workflows.
- Add branch/update guidance for local canary/high-extreme development.

### Phase 4 - Org rollout

- Build the repo inventory and migration tracker.
- Create repeatable project-spec templates.
- Migrate projects in waves, oldest-first where applicable.

## Design constraints

- No seed SQLs as the standard operator path.
- Keep CLI, MCP, and API aligned to the same object model.
- Favor explicit, auditable mutations over implicit magic.
- Keep docs and session artifacts first-class.
- Do not make the queue a dead-end placeholder.

## Cross-project reuse opportunities

- The import bundle schema should be reusable across repos.
- The release-channel adapter and promotion gate logic should be reusable across repos.
- The migration tracker and project-spec template should be reusable across repos.
- The CLI command map and docs patterns should be reusable across repos that adopt AgilePlus.
