### Current Memory System (Phase 5B)

```
Storage:     ~/.claude/civilization/agents/{agent_id}/memory.jsonl
Format:      Line-delimited JSON, one memory per line
Operations:  store, query, stats, purge, clear
Query Types: by type, by time range, by importance
Limitation:  Linear scan for every query (O(n))
```

### Known Limitations
- No index: Every query scans all memories (slow for large datasets)
- No relationships: Memories are isolated per agent
- No search: Can't find memories by content keywords
- No analytics: Can't detect patterns or trends
- No sharing: Agents can't learn from each other's memories
- Unbounded growth: Old memories need manual purge

## Phase 6 Architecture

### 6.1: SQLite Backend Migration

**Goal**: Upgrade from JSONL to SQL database for better performance

```
Current (JSONL):
├─ ~/.claude/civilization/agents/{agent_id}/memory.jsonl
└─ Memory file (line-delimited JSON)

Phase 6 (SQLite):
├─ ~/.claude/civilization/memories.db (single file)
├─ Tables:
│  ├─ memories (id, agent_id, type, timestamp, content, importance)
│  ├─ memory_relationships (memory_id, related_memory_id, strength)
│  └─ memory_index (content_hash, keyword, memory_id)
└─ Indexes:
   ├─ agent_id + timestamp
   ├─ agent_id + type
   ├─ timestamp DESC
   └─ importance DESC
```

**Benefits:**
- Indexed queries (O(log n) vs O(n))
- Atomic transactions
- Relationship tracking
- Single file (easier backup)
- Atomic purges

**Compatibility:** Provide migration tool (JSONL → SQLite)

### 6.2: Full-Text Search

**Goal**: Index and search memory content

```
MemoryService.search_memories(agent_id, query: str) -> List[AgentMemory]
# Example: search_memories("project-a", "database optimization")

# Under the hood:
# 1. Parse query → keywords
# 2. Search memory_index table
# 3. Rank by TF-IDF
# 4. Return top 10 results
```

**Schema:**
```
CREATE TABLE memory_index (
    id INTEGER PRIMARY KEY,
    memory_id TEXT,
    keyword TEXT,
    frequency INTEGER,
    FOREIGN KEY(memory_id) REFERENCES memories(id)
);

CREATE INDEX idx_keyword ON memory_index(keyword);
```

**Performance:**
- Initial indexing: <100ms (per memory)
- Search: <10ms (100 keywords)
- Index size: ~20 bytes per keyword

### 6.3: Memory Relationships

**Goal**: Link related memories within and across agents

```
# Within agent: "I learned X, which helps with Y"
MemoryService.link_memories(memory1_id, memory2_id, strength=0.8)

# Across agents: "Agent A's learning helps Agent B"
MemoryService.link_memories(
    memory_from_agent_a,
    memory_from_agent_b,
    strength=0.6,
    cross_agent=True
)
```

**Schema:**
```
CREATE TABLE memory_relationships (
    id INTEGER PRIMARY KEY,
    memory_id_1 TEXT,
    memory_id_2 TEXT,
    strength REAL (0.0-1.0),
    relationship_type TEXT (caused_by, helps_with, similar_to, contradicts),
    created_at REAL,
    FOREIGN KEY(memory_id_1) REFERENCES memories(id),
    FOREIGN KEY(memory_id_2) REFERENCES memories(id)
);

CREATE INDEX idx_memory1 ON memory_relationships(memory_id_1);
CREATE INDEX idx_memory2 ON memory_relationships(memory_id_2);
```

**Use Cases:**
- "This error is caused by that earlier decision"
- "This learning helps with that other learning"
- "This is similar to that previous experience"

### 6.4: Memory Analytics

**Goal**: Detect patterns and trends

```
MemoryService.get_learning_trends(agent_id, days=30) -> Dict:
    # Returns: trending keywords, peak learning times, etc.

MemoryService.get_agent_patterns(agent_id) -> Dict:
    # Returns: decision patterns, error clusters, success factors

MemoryService.compare_agents(agent_id_1, agent_id_2) -> Dict:
    # Returns: similarity score, complementary skills, learning opportunities
```

**Calculations:**
```
Learning Velocity:  # of learnings per day
Error Density:      # of errors per day
Success Pattern:    Errors / Executions by time
Keyword Trends:     Most common keywords over time
Skill Overlap:      Shared memories between agents
```

**Storage:**
```
CREATE TABLE memory_analytics (
    id INTEGER PRIMARY KEY,
    agent_id TEXT,
    metric_type TEXT (learning_velocity, error_density, success_pattern),
    metric_value REAL,
    timestamp REAL,
    period TEXT (daily, weekly, monthly),
    FOREIGN KEY(agent_id) REFERENCES agents(id)
);
```

### 6.5: Memory Sharing & Learning

**Goal**: Allow agents to learn from each other

```
# Agent B queries Agent A's learnings
shared_memories = MemoryService.get_agent_learnings(
    source_agent_id="project-a:agent-1:L1:researcher",
    target_agent_id="project-a:agent-1:L2:builder",
    min_importance=0.7
)

# Create relationship showing Agent B benefited
MemoryService.record_learning_transfer(
    source_memory_id=learning_id,
    target_agent_id=target_agent_id,
    applied_at=now,
    effectiveness=0.9  # How effective was this learning?
)
```

**Schema:**
```
CREATE TABLE learning_transfers (
    id INTEGER PRIMARY KEY,
    source_memory_id TEXT,
    target_agent_id TEXT,
    transfer_timestamp REAL,
    effectiveness REAL (0.0-1.0),
    feedback TEXT,
    FOREIGN KEY(source_memory_id) REFERENCES memories(id)
);
```

**Security:**
- All memory access is read-only
- Agents can't delete or modify shared memories
- Transfer tracking provides audit trail

## Design Decisions

### 1. SQLite over Other Databases
**Why SQLite:**
- Single file (no server setup)
- No external dependencies
- ACID transactions
- Full-text search support (FTS5)
- Perfect for local agent storage

**Considered:**
- PostgreSQL: Overkill, needs server
- MongoDB: Overkill, No FTS
- DuckDB: Good, but SQLite more universal

### 2. Abstraction Layer (MemoryStorage Interface)
**Why:** Support multiple backends
```
class MemoryStorage(ABC):
    @abstractmethod
    def store(self, memory: AgentMemory) -> bool: ...
    @abstractmethod
    def query(self, agent_id: str, ...) -> List[AgentMemory]: ...

class SQLiteMemoryStorage(MemoryStorage): ...
class JSONLMemoryStorage(MemoryStorage): ...  # Fallback
```

### 3. Optional SQLite Migration
**Why:** Gradual rollout, fallback path
- Phase 6a: SQLite available alongside JSONL
- Phase 6b: Automatic migration on first use
- Fallback: If SQLite fails, use JSONL

### 4. Full-Text Search via Custom Indexing
**Why:** Better control than relying on SQLite FTS5
- Custom keyword extraction
- TF-IDF scoring
- Domain-specific scoring (error > learning > decision)

### 5. Relationship Strengths (0.0-1.0 scale)
**Why:** Enable probabilistic reasoning
- 0.8: Strong relationship (high confidence)
- 0.5: Medium relationship
- 0.2: Weak relationship
- Agents can weight recommendations by strength

## Known Risks & Mitigations

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|-----------|
| SQLite file corruption | Low | High | Automatic backup, rollback to JSONL |
| Search performance (large datasets) | Low | Medium | Index optimization, incremental indexing |
| Memory relationships bloat | Medium | Medium | Garbage collection, strength threshold |
| Analytics computation expensive | Medium | Low | Async computation, caching |
| Cross-agent sharing privacy | Low | High | Read-only access, audit log |
