## Result
### WL-331 Connector queue initiative
- Backlog entry WL-331 is explicitly a queue/resume effort for connector reliability, so the starting guardrail is the same description as WL-332 and the accompanying evidence stream from `docs/reference/WORK_STREAM.md:26865-26884`.
- Remote write failures already land in a deterministic dead-letter store: `RemoteWriteDeadLetterQueue` serializes `RemoteWriteDeadLetterRecord` objects to `docs/reference/workstream_remote_writes_dead_letter.jsonl`, persists per-source/backoff settings, and exposes `candidates_for_replay()` sorted by `next_attempt_at` for deterministic replays (`src/thegent/sync/dead_letter_queue.py:170-248`).
- The `sync` command writes its raw errors into that queue when it fails to publish board items, respecting the same configurable path/backoff env overrides used by WL-331 (`src/thegent/commands/sync.py:1070-1143`).
- Replaying those queued entries is already scoped by `DeadLetterReplayEngine`, which iterates the queue, invokes a handler, and rewrites retry counters so the queue never loses deterministic ordering if the handler fails (`src/thegent/integrations/dead_letter_replay.py:1-124`).
- The autosync runner keeps an in-memory `SyncFailureQueue` that is rehydrated from `docs/reference/workstream_autosync_failures.json` before every cycle, capturing transient connector failures and pruning anything older than `failure_queue_retention_seconds` (`src/thegent/integrations/workstream_autosync_shared.py:582-630`, `src/thegent/integrations/workstream_autosync.py:128-2059`).
- These pieces together cover the existing queue/resume plumbing, so WL-331 can now focus on wiring the replay engine into the lifecycle, publishing depth/age telemetry and forcing deterministic replays when connectors recover.

### WL-332 Connector throttle initiative
- WL-332 shares the same high-level description in `docs/reference/WORK_STREAM.md:26865-26884` but is scoped toward throttling behavior rather than queue persistence.
- Autosync consumes a `RateLimitBackoffManager` with `RateLimitConfig` parameters derived from the runner config (max retries, initial wait, max wait, multiplier) to detect 429/503 responses and compute jittered exponential backoff before retrying (`src/thegent/integrations/rate_limit_backoff.py:1-165`).
- The same runner instantiates that manager (`_rate_limit_backoff`) and holds it alongside the failure queue, slotted into every connector cycle so each loop can `compute_wait` before hitting downstream providers and keep the throttle decisions traceable when they fire (`src/thegent/integrations/workstream_autosync.py:128-193`).
- With the queue and throttle machinery co-located, WL-332 can now focus on surfacing throttle audits (backoff duration, attempt count) and verifying that the Tenacity retry decorator generated by `RateLimitBackoffManager.make_retry_decorator()` is wired into connector write paths.
